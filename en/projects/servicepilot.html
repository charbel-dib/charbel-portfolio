The problem

Answering a support question often requires multiple tools. Giving an agent write access introduces another question: who authorises exactly which action?

02

Technical decisions

01

Three read-only tools

Search authorised procedures, call a status API and retrieve incidents. The model has no direct ticket-creation tool.

02

A proposal before an action

The proposed content is frozen and linked to an owner, digest and expiry. The server checks approval and permissions when writing.

03

A resumable workflow

LangGraph and SQLite persist state. Ticket creation is idempotent to avoid duplicates on resumption.

03

What the project delivers

A locally runnable SDK, API and support workspace, with tests, evaluation scenarios, Docker Compose and CI workflows. The default mode is deterministic and uses no LLM; an optional OpenAI adapter is available.

What I take from it

Treat permissions and approval as software rules, independent of instructions given to the model.

Scope & limits

Proof of concept using fictional data. Offline tests do not establish real-model quality or general prompt-injection resistance. The current version uses static tokens and a local SQLite database.
