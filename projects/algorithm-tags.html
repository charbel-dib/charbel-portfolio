Algorithm tags.

Prédire les tags algorithmiques d’un problème de programmation à partir de son énoncé et de sa solution.

4 982 problèmes Codeforces, 8 tags, dont 46 % sans aucun tag : F1 macro9 de 67,5 en validation croisée contre 64,4 pour un SVM sur l’énoncé seul.

01

Ce que le projet produit

F1 macro9 de 67,5 en validation croisée contre 64,4 pour la référence, devant à chacune des 4 répétitions ; 65,7 contre 64,6 sur le test, tenu à l’écart de toute décision.

Suite envisagée

Suite envisagée : un encodeur de code fine-tuné, comparé à ces SVM sur le même protocole.

02

Le problème

Un problème peut avoir plusieurs tags ou aucun. Un modèle qui tague tout semble bon sur les tags fréquents mais se trompe sur près de la moitié des problèmes.

03

Les choix techniques

01

Mesurer aussi l’absence de tag

F1 macro9 : les 8 tags plus l’état « aucun tag », traité comme une 9e classe et utilisé comme critère de sélection.

02

Lire le code, pas seulement l’énoncé

Six blocs de features, dont les jetons de l’AST Python de la solution, la difficulté et les exemples d’entrée/sortie.

03

Préférer le modèle simple quand il suffit

Environ 130 variantes essayées (LightGBM, MLP, embeddings gelés, stacking) ; aucune ne justifiait sa complexité face aux SVM linéaires.

04

Évaluation

Validation croisée répétée sur train + validation, test évalué une fois ; intervalles par bootstrap ; résultats par tag et matrices de confusion publiés dans le dépôt.

Ce que j’en retiens

Choisir la métrique qui reflète l’usage réel avant de choisir le modèle.

05

Périmètre & limites

Sur le test seul, l’écart (1 point) reste dans l’intervalle de confiance (±2,5 points) : c’est pourquoi les choix reposent sur la validation croisée. Les confusions trees/graphs et number theory/math viennent en partie d’annotations floues.
